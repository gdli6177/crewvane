# Crewvane 0.6 产品方向与目标详情重构

状态：评审基线。基于 `v0.5.1` 的实现和目标弹窗真实截图整理。

## 1. 产品判断

Crewvane 的第一价值不是让用户更快地管理 Agent，而是让用户同时推进很多事情时，仍然只被真正需要人的变化打断。用户不应该记住哪个终端在运行、哪个目标正在等待、哪条审批还没有回复，也不应该为了推进一件事在多个会话之间来回寻找上下文。

因此 0.6 继续坚持三个边界：

1. **注意力是主界面**：用户先看“现在需要我做什么”，而不是先看 Agent、终端或运行状态。
2. **事实与解释分离**：Agent 的消息保持非结构化原文；状态、等待、验收和授权只能通过显式命令写入。
3. **核心窄、适配器可选**：Herdr、通知、Agent 发现、外部系统和富视图都通过适配器接入。可选组件失效时，目标仍能记录、查看、追问和验收。

## 2. 管家层是否应该存在

### 结论

**保留管家，但把它改成不可见控制面服务。**

管家层有价值，因为它承担跨目标的事务：

- 排序和分发新目标；
- 为目标创建或复用负责人；
- 在等待到期、负责人阻塞、会话失效时恢复现场；
- 把多个目标的异常合并成一次需要人的处理；
- 检查交付是否有成果、位置和真实检查记录；
- 保证同一事实不会重复提醒、重复派发或重复创建会话。

这些是跨目标协调，单个负责人天然看不到，也不应该让用户手工维护。

### 问题不在“有管家”，而在“把管家做成了第二个聊天入口”

如果每件事都要先和管家聊一轮，产品就会变成另一个会话列表。用户仍然要判断应该找谁、上下文在哪里、这件事是否已经同步，注意力问题没有消失。

0.6 的产品形态应是：

```text
桌面 / Herdr 插件 / CLI
          │
          ▼
   目标与注意力（用户入口）
          │
          ▼
 管家服务（默认不可见）
   ├─ 分发与恢复
   ├─ 跟进与去重
   ├─ 交付完整性检查
   └─ 升级需要人的事项
          │
          ▼
     负责人（可问责执行）
```

管家默认没有独立聊天首页。用户可以：

- 在目标弹窗中补充一句自然语言；
- 在注意力项中决定、退回或验收；
- 在异常时点击“找管家”进入现场；
- 在设置中检查管家状态。

管家可以继续在 Herdr 中运行，但正常流程不要求用户打开它的终端。

### 取舍

- 不做管家：跨目标恢复、排序、去重和异常归并没有可靠责任主体。
- 把管家做成主聊天入口：用户仍然需要管理对话，违背注意力中心。
- 把管家完全自动化但不保留现场：阻塞和适配器故障无法排查。

推荐采用“不可见服务 + 显式故障现场”的组合。管家应是**控制面**，不是第二套状态源。

## 3. 单负责人还是临时小队

### 默认：一个目标一个负责人

负责人对结果、下一步、交付和向上沟通负责。默认只有一个负责人，原因不是组织层级，而是可问责性：

- 用户和管家总有一个明确对象可以追问；
- 成果和验收有单一汇总点；
- 不需要提前决定工人数量、角色和通信拓扑；
- 大多数目标不值得承担多人协作的上下文同步成本。

### 何时引入 worker

只有同时满足以下条件才建议创建临时工人：

1. 至少有两个可以独立交付、文件或接口范围不冲突的工作流；
2. 并行节省的真实时间明显高于协调、合并和验证成本；
3. 负责人能写出每个工人的输入、输出和验收条件；
4. 负责人有时间合并结果并承担最终验收。

典型情况是独立模块、并行调研、互不覆盖的测试和资料整理。只因为“任务看起来大”不应自动扩队。

### 小队约束

- 工人由负责人按需创建和关闭，不由用户逐個管理。
- 第一版最多两名工人，不嵌套小队。
- 工人只向负责人汇报，不直接升级给用户。
- 负责人负责拆解、合并、验证和最终交付。
- 工人是目标执行详情中的临时事实，不是全局固定编制。

### 避免管理复杂的方式

目标弹窗默认只展示一个负责人和一句“当前无并行工作 / 2 名工人正在执行”。展开后才显示工人、范围和状态。工人失败先由负责人重新分配或自己处理；负责人无法恢复时才交给管家，管家仍不能解决才进入注意力。

## 4. 是否提供外部 Agent Skill

### 结论

**提供，而且应作为正式集成面。**

Codex、Claude Code、Cursor、OMP 等 Agent 已经运行在用户自己的终端里。要求用户切换到 Crewvane UI 才能登记目标，会丢掉“任务正在哪里产生”的上下文。

外部 skill 的职责是把 Agent 引导到稳定的 CLI，而不是让它直接改 `.crewvane/state.json`：

```text
外部 Agent
   │
   ├─ crewvane ask / goal message    人可提交原文，不猜状态
   ├─ crewvane goal show / list      读取结构化事实
   └─ crewvane goal progress / wait / review / decide
                                        负责人或管家在事实发生后提交
```

Skill 必须明确：

- `message` / `direct` 只追加原文，不改变状态；
- 进展、等待、交付、决定必须由有权限的负责人或管家显式提交；
- Agent 不得代替人批准、验收、放弃或删除；
- 无法确认目标归属时，不猜测，也不混入其他目标；
- 终端中的自然语言不会自动变成目标状态。

安装入口应放在设置中，按 Agent 检测可写的 skills 目录，仅更新带 Crewvane 标记的版本，绝不覆盖用户同名 skill。Skill 是可选适配器；未安装时桌面、Herdr 和 CLI 仍可独立工作。

## 5. 执行前方案与 acceptance brief 放在哪里

### 结论

**讨论可以发生在外部，执行合同必须落在 Crewvane。**

用户真正需要的不是另一个规划页面，而是避免“方案没想清楚就开工”。因此：

1. 用户可以在 Codex、Cursor 或任意对话环境里先把问题聊清楚。
2. 外部 Agent 将商定结果整理成一份紧凑的 **Execution Brief**。
3. Brief 通过 CLI 写入 Crewvane，成为负责人开工前的共同依据。
4. 复杂、高风险或会产生外部影响的任务，由人明确确认一次方向。
5. 简单任务可以跳过人工确认，但仍保留自动生成的 brief。

### Execution Brief 的最小字段

```text
目标结果
验收标准（可观察、可检查）
约束与禁止项
关键未知项
执行计划
是否需要 worker，以及并行边界
```

Brief 可以是 Markdown 原文加少量显式字段。Crewvane 不需要拆解 Agent 的聊天记录，也不需要把每个观点变成表单。

### 取舍

- 全部留在外部：执行中失去共同验收依据，管家和负责人容易理解不一致。
- 全部搬进 Crewvane：重复成熟对话工具的上下文管理，产品变重。
- 在 Crewvane 内新建“方案聊天”：容易出现第二套会话和事实源。

推荐“外部讨论、内部固化”：Crewvane 只保存承接口头讨论后的执行合同和后续事实，不负责替代思考过程。

## 6. 目标详情重构

### 0.5.1 的真实问题

从注意力进入目标弹窗时，用户需要先越过标题、元数据和一段“最近记录”，才能在底部操作；完整对话又被折叠在更低的位置。决策时看不到依据，验收时证据和动作不在同一视野。运行时错误还会作为显眼的事实挤进目标内容。

这导致用户只能点“找管家”或“回到现场”，因为目标弹窗没有完成“决策和验收所需的信息组织”。

### 0.6 信息架构

```text
目标弹窗
├── 顶部：项目 / 模式 / 状态 / 找管家或回到现场
├── 左栏：现在需要你做的事
│   ├── 为什么进入注意力
│   ├── 下一步
│   ├── 最近一次有效交接
│   ├── 交付摘要与检查证据（验收态）
│   ├── 目标原文（可展开）
│   ├── 图片附件
│   └── 系统错误与目标管理（次级折叠）
├── 右栏：对话与交接
│   ├── 人的原话
│   ├── 管家与负责人的回复
│   ├── 决定、交付、退回记录
│   └── 最新在上，系统事件单独折叠
└── 底部：只显示当前状态需要的决定或验收动作
```

左侧回答“现在是什么、我凭什么处理、处理后会怎样”，右侧回答“这件事怎么发展到这里的”。动作区不再重复大段上下文。

### 决策流

1. 用户从注意力点击决定事项。
2. 首屏直接显示问题、决定后的安排和最近一次有效交接。
3. 右侧显示完整对话，最新内容在上。
4. 用户可以直接写决定并批准或拒绝，也可以先补充意见。
5. 自然语言只新增消息；只有“批准 / 拒绝”按钮写入决定账本。

### 验收流

1. 待验收目标首屏直接显示交付摘要、位置、检查项和结果。
2. 对话保留在旁边，供用户确认修改历史。
3. 用户可以退回修改并写原因，或明确验收通过。
4. Agent 自称完成、终端空闲或 Herdr `done` 都不产生验收按钮。

### 跟进流

到点跟进只提供一个自由输入框：

- 人描述当前情况，例如“审批通过”“还在等”或“这件事结束”，点击“交给管家”；外部等待交回 Agent 时先恢复跟进中并清除旧等待与提醒，由管家核查后重新确定安排；普通消息不清除尚未解决的决定、验收或介入。
- 管家读取原话后决定继续等待、恢复推进、验收、结束或放弃；完成、放弃和批准必须把用户原话写入操作记录。
- “1 小时后提醒”是唯一独立次级动作，不冒充完成、继续或验收。

## 7. 模块化与 CLI 边界

目标详情只依赖视图模型和一个窄服务接口：

```ts
interface GoalDetailService {
  command(command: CrewvaneCommand): Promise<unknown>;
  importAttachments(inputs: AttachmentInput[]): Promise<GoalAttachment[]>;
  previewAttachment(goalId: string, attachmentId: string): Promise<string>;
  openAttachment(goalId: string, attachmentId: string): Promise<void>;
  openHerdr(goalId: string): Promise<void>;
  openUrl(url: string): Promise<void>;
  retryDispatch(goalId: string): Promise<void>;
}
```

约束：

- UI 不读取 Herdr 日志来猜状态，也不解析 Agent 自然语言。
- UI 只展示 core 中的原始 `Activity`，并用结构化 `delivery`、`attention`、`status` 决定操作。
- 第三方富视图只能增强只读展示；决定、验收、退回仍调用标准命令。
- CLI 和桌面共用同一个 core 服务、锁和原子存储。
- Herdr、通知、Agent skill 安装、外部集成都是可替换适配器，不是目标事实的必要条件。
- 插件失效只影响对应能力；新增消息、目标记录和人工验收继续可用。

## 8. 最小版本范围

0.6 首版应控制在一组能够真实节省管理成本的能力：

1. 管家的常规交互收进目标内，不再要求打开管家聊天。
2. 一个目标默认一个负责人。
3. 临时小队作为负责人内部的可选执行详情，最多两名工人。
4. 目标详情采用“工作区 + 对话”双栏结构。
5. 决定与验收在目标弹窗内获得完整依据和明确动作。
6. 提供可安装的 Crewvane Agent Skill，只包装稳定 CLI。
7. Execution Brief 作为显式、紧凑的目标产物；外部先讨论，内部再固化。
8. Herdr、通知和 skill 安装保持可选适配器。

暂不进入首版：

- 固定工人角色和组织图；
- 自动从任意终端内容推断进度；
- Crewvane 内置又一个 AI 规划聊天；
- 为每个目标创建全局管家；
- 插件市场、远程动态插件或复杂权限编排。

## 9. 验收标准

### 产品体验

- 用户从注意力打开决定事项后，不打开终端即可看到问题和最近有效依据。
- 用户从注意力打开验收事项后，不滚动即可同时看到交付摘要和明确验收动作。
- 对话按时间倒序，最新记录在上；系统错误不再混进 Agent 交接。
- 目标原文和附件可追溯，但不抢占当前动作。
- 深色、浅色和 1024px 窗口下无横向溢出，正文和底部动作不互相遮挡。

### 状态与权限

- 普通消息不会改变目标状态、授权或验收。
- Agent 不能代替人批准、验收、放弃或删除。
- 只有显式状态命令能产生等待、交付、完成等事实。
- 外部 Agent 未主动写回时，其终端聊天只存在于现场，不被猜测进目标历史。

### 模块与恢复

- 移除 Herdr、通知或 skill 安装后，目标记录、消息和人工验收仍可用。
- CLI 与桌面并发写入不会丢目标或覆盖其他目标。
- 管家或负责人会话恢复失败时，目标、队列和注意力保持，界面提供可操作错误。

### 真实试用

- 至少用两个项目和五个混合状态目标验证。
- 完成一次决定、一次退回、一次重新交付和一次验收通过。
- 在外部 Agent 中通过 CLI 追加消息，验证桌面即时刷新且状态不变。
- 关闭并重启后，目标、对话、提醒和注意力保持一致。
