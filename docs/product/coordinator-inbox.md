# 持久协调收件箱

## 目标

多个目标同时产生消息时，唯一管家仍必须在干净、单一案卷的上下文中处理每一条通知。目标负责人可以并行执行；需要管家判断、转交或收口的事件必须串行，且不能因为应用重启、Herdr 超时或一个目标失败而丢失。

## 数据结构

每个工作区保存 `.crewvane/coordinator-inbox.json`：

- `human`：用户明确反馈、现场回执、重启与人工操作。
- `attention`：到期跟进、阻塞或负责人不可达等需要优先核查的事件。
- `normal`：新目标与普通状态变化。
- `background`：无进展、空闲回执与周期性核对。

同一目标只保留最新有效请求。新请求优先级不低于旧请求时替换旧请求；旧请求优先级更高时，新请求直接记为 `coalesced`。已经发送中的请求不会被新请求篡改，后续请求等当前请求完成后再处理。

终态记录最多保留 240 条，超出时只裁剪最旧的 `sent`、`failed`、`unconfirmed`、`cancelled` 与 `coalesced` 记录。`queued` 和 `processing` 永不因容量裁剪。状态中的失败和未确认数量按每个目标最新记录计算，成功重试后不会一直显示旧错误。

## 调度与恢复

调度器在一个工作区内只有一个串行 drain：

1. 按优先级和入队顺序认领一条请求。
2. 目标通知或巡检在发送前原子写入本次 `goalId` 与 `requestId` 的 scope。
3. 等待管家回合的确定结果。
4. 写入 `sent`、`unconfirmed`、`failed` 或 `cancelled`，再处理下一条。

单个目标失败不会阻塞其他目标。Herdr 明确报告 blocked 时会暂停自动重试；结果未确认且现场仍为 `working` 时也暂停，避免向正在执行的同一管家重复插入请求。下一次同步、新事件或用户操作会重新触发 drain。

应用启动时：

- `queued`：继续处理。
- `processing`：转为 `unconfirmed`，保留说明并停止自动重放，因为进程退出前请求可能已经交给管家。
- 没有遗留请求：正常启动。

用户侧看到的顶部状态分别显示当前处理目标、排队数、最新失败的待重试数或未确认的待核对数。

## 上下文轮换

累计完成 40 个案卷，或累计估算字符达到 240,000 后，应用在满足以下全部条件时轮换管家：

- 收件箱没有 queued 或 processing。
- 管家处于 `idle` 或 `done`。
- Herdr 与 CLI 可用。

应用关闭旧管家，重新准备同一身份，再清零本轮上下文预算。目标、消息、附件、交付、决定、活动历史和 Herdr 负责人现场不参与清理。轮换失败只显示可重试诊断，队列和新目标继续可用。

## 性能边界

协调收件箱优化的是排序、合并与持久化，不会加速模型本身。每个案卷仍需要一个完整管家回合，单回合观察上限为 30 秒。负责人执行与其他工作区不受单一管家 turn 串行限制。

本地基准提交 20 个目标 × 5 条混合事件，共 100 条：

- 最终协调通知：20 条，合并 80 条。
- 持久化入队 p95：约 0.5–1 ms。
- 模拟每个管家回合 50 ms 时，串行排空约 1.1 秒。
- 无剩余 queued。

该结果表示本地队列不是主要瓶颈。真实处理时间取决于所配置 Agent 的模型、工具与网络回合。

## 验收

- 100 条事件只为 20 个目标产生 20 条最新通知。
- 人工消息优先于普通目标和后台巡检。
- 低优先级事件不能覆盖排队中的人工消息。
- 一次失败后继续处理其他目标。
- 应用在发送中退出后不自动重放，未开始工作可以恢复。
- 每次目标与巡检发送前 scope 都指向本次请求。
- 旧请求不能确认或覆盖新请求。
- 40 个案卷后只在管家空闲时轮换，旧目标与交付完整。
- 顶部状态在成功重试后清除旧失败计数。
