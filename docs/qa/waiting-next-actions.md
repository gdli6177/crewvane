# 等待事项对话收口验收

日期：2026-11-04。基于 v0.4.2 修复。

## 原因

等待中的目标把“更新下一步”“记录决定”和“记录进展”藏在手动表单中。编辑安排虽然能恢复状态，却不是清晰的动作；`goal.progress` 还可能只写记录而不通知管家。普通等待目标也没有要求立即核查进展或修改提醒的直接入口。

## 操作

- 到点跟进与普通等待只突出一个“告诉管家”自由输入框。人可直接写结果、仍在等待、结束或放弃，不再选择语义相近的“补充、跟进、继续”按钮。
- 消息保存后立即清除该次提醒注意力，但目标仍保持 `waiting`；唯一的全局管家收到唯一案卷 ID 和新增原话，再决定继续等待、恢复推进、验收、完成或放弃。
- “1 小时后提醒”是唯一独立次级动作，保留等待状态并按新时间重新进入注意力。
- 完成、放弃、验收和批准必须由用户明确表达。管家执行时把用户原话写入 `--note` / `--reason`，活动记录同时保留操作者与原文。
- 高级手动操作明确分为「补充进展」「编辑目标」「提交成果」。补充进展不覆盖原定的下一步，编辑目标不提交验收，提交成果必须附真实检查。

## 状态与通知

“告诉管家”使用持久化的 `dispatch` 请求，有 `pending`、`sent`、`failed` 三种可见状态。消息发送前先保存更新，失败保留内容和重试入口；打开工作区会重试尚未完成的请求。每次请求有独立 ID，旧消息回执不能覆盖更新的对话、状态写回或人工接管。重复请求在后台合并，成功送达后不再自动补发同一请求。

管家更新消息明确包含用户原话。只有当用户语义明确时才执行状态命令；含糊的回复先追问；结束类命令保留用户原话作为审计依据。消息送达本身不改变目标状态，也不代表外部人员已经回复。

## 验证

`packages/core/test/waiting.test.ts`、`cli/test/cli.test.ts` 与 `apps/desktop/test/goal-delivery.test.ts` 覆盖对话清除提醒、状态保持等待、受管管家结束原话审计、稍后提醒、手动接管、离线失败和重试、旧回执、并发新请求、重启读取及结束目标拒绝恢复。

`pnpm test:desktop` 通过真实打包界面完成等待、设置提醒和对话收口；`pnpm test:onboarding` 通过真实可交互 CLI 验证“告诉管家”的实际 stdin，并确认用户消息本身不抢先改变目标状态。自定义 CLI fixture 证明真实消息传输，不冒充真实模型已经理解或完成。

完整桌面试用、首次启动和安装包验收均已通过。类型检查与 49 项单元测试通过；DMG、ZIP 完成 SHA-256、严格签名、下载隔离、安装启动、图标和内置 CLI 写入验证。首轮桌面回归发现到期跟进注意力遮住了恢复后的普通进展入口，已修正等待状态的操作边界并重跑。新增 onboarding 用例在关闭目标后需先回到设置，再执行原有的打开 Herdr 验证。
